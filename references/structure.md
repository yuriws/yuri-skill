# 防 O(n²) 膨胀

长篇改写的真正瓶颈不是写正文，是**文档结构**。这一份是硬约束与做法。

## 5.0 ⚠️ 最贵的成本不是写正文，是**维持「每轮必读」的上下文**

（口径：**轮＝一章**，默认每10章一批。批尾先保存检查与接续记录；是否换会话按上下文长度和用户安排，不要求每批新建会话。）

实测：压缩文档消耗的额度比正文改写还多。根因**不是压缩技巧差，是「每轮必读」清单本身选错了**：

| 误放进每轮必读的东西 | 真实使用频率 | 处置 |
|---|---|---|
| 拉人物出场表、校验清单、批注格式 | **每批一次** | 下沉 DETAIL（＝`RULES-DETAIL.md`，触发条件见 init.md 第二块） |
| 设定表的静态块（作品事实 / 术语 / 主角基线 / 结局） | **几乎不变** | 拆静态层 |
| 规则核心层里与正文清单重复的长尾索引 | 已在正文节列出 | 索引只留 DETAIL 专属条目 |

**四条结论，做新项目时直接套**：

1. **区分「规范」与「做法」**。规范＝改文时随手要用（硬护栏、称呼表、人物关系、描写基线、隐性错误清单），必须常驻；做法＝工具使用方法（拉表、校验、写批注、批尾同步），**批级频率，批首读一次就够**。**把做法塞进每轮必读＝为一次批尾动作付每轮的钱。**
2. **「不读」比「读得短」更重要**。静态层拆出去后**每轮开销直接归零**，比任何压缩都有效。
3. **上限改软目标**。硬上限会逼出**无意义的措辞挤压**——为了凑数字改写句子，既伤内容又费 token，还制造「文档必须反复维护」的错觉。**软目标 + 真溢出才整条下沉**。
4. **压缩前先量「固定 vs 可变」**（见 5.1），同样适用于规则库：**先问「这条每轮都要用吗」，再问「怎么压短」。**

## 5.1 接续摘要：按检索需要选择，不由正文载体决定

**目标**：换会话仍能找到进度、必要前情与待办。默认直写卷可用章号、短引文、设定及批注定位，不另建重复摘要；单章、卷、Word等载体均先核现有入口是否够用。确需摘要时沿用现有接续位置分层保存，不能因载体不是单章就拒绝必要接续，也不默认每本另造摘要容器。以下为有摘要时的维护方法：

- **绝不把摘要抄进第二个文件**：每章文件末尾带累计摘要，是 O(n²) 冗余，长篇数学上不可行。
- **分层**：L0 最近 ≤10 章逐章详情 / L1 每批一条 / L2 压实——**让每轮上下文有天花板**。
- **定上限前先量「固定 vs 可变」占比**，不要按章数拍脑袋。可用窗口 ＝ 上限 − 固定部分；固定区块（头部说明 / 人物状态表 / 待办）常吃掉一半以上预算，导致「每加一章都要压」。
- **人物状态表不进摘要**：与设定表重复，且每多一个角色永久多占几十字。放进设定表，净成本为零。
- **压实按条数触发，不按批触发**：写成「窗口 >10 条就压最老的 5 条」，峰值可控；写成「每批压一次」，批中会出现峰值顶破上限。
- **历史弧线本身也 O(n) 增长**，要单独分层压实，且**配额按实测调整，不预设远期数字**。

## 5.1b 设定表也会膨胀，但**不能蒸馏**

| | 滚动摘要 | 设定表（字典） |
|---|---|---|
| 增长方式 | **累积式**——每章产生新事件，天然 O(n) | 主体**更新已有条目**——已定称呼变更时更新对应字段；新人物或新约束才新增 |
| 真正的增量 | 全部 | 只有**角色表**和**术语表** |
| 能否蒸馏 | **能**——丢了细节还有正文卷兜底 | **不能**——概括完就不是字典了 |
| 治理手段 | 分层压实 | **分层归档 + 退出机制**（按需 grep，不每轮读） |

**为什么蒸馏对字典是破坏性的**：「某角色＝女，某种族战士，可靠温柔」一旦被概括成「闺蜜团之一」，下次写到她就完全不知道该怎么改。**设定表的价值就在于可直接查用的确定性。**

**跨题材的设定保存与归档原则**：按人物重要性、后续作用及检索需要组织设定，字段服从本书；都市职业、仙侠师承、历史辈分／爵位等只是例子。

- **设定表不设文件级字数上限**：移出「每轮必读」后**保留完整决策事实，状态变化更新对应记录，不为凑字删事实**，靠下面的**条目级退出机制**治理，两者是不同层级。
- **归档按本书已定标准复查重要性及后续作用**：久未出现只是线索，不自动归档或改变处置。项目可采用连续30章等复查窗口，但须结合后续线索、核心关系和检索需要；既有项目沿用其更具体约定。
- **核心及未收束约束持续可查**：亲属、重要同伴、长期对手、用户指定长期人物及未收伏笔按本书要求保留入口，不因未出场就移走。角色处置是否已定与是否活跃是不同维度，归档不重新决定其性别；未定事项仍保留待核状态。
- **归档 ≠ 失忆**：移走时把条目**移入**（不是复制）归档层。改文拉「人物出场表」时**先 grep 活跃层 + 归档层再判断**。**退太早的真正代价不是 grep 成本（很便宜），而是把回来的角色当新角色重新定性 → 产生不一致。**
- **归档保留全部影响后文写法的已定事实及有效指针**：原名／新名、性别处置、称呼、人物内核，以及已定相貌、身形、声线、形象变化、身份、关系及伏笔约束等，按实际需要保存，不设30—50字目标。整条移动或有可追溯字段，去掉的仅是无须作为设定保存的情节流水。CAST等导航卡可精简，不把卡的短字段当成权威设定的删减标准。
- **为什么归档层变大不增加开销**（分层的全部意义，容易被误解）：**归档层不进上下文**，只有 grep 命中时才碰，而 grep 只回传**匹配行**而非整个文件。归档层涨到 5 万字，每轮成本仍是 **0**。
- **准入按后续约束判断**：一次性NPC、无名角色若无后续相关决定，可只记批注；若其身份、称呼、承诺或伏笔影响后文，则保存必要事实及位置。不以有无姓名或是否已多次出场作为记设定的唯一条件。
- **动态进度入口只留当前需要的线索**：已收尾的流水可移出；仍影响后文的身份、关系和认知约束保留在权威设定或可查历史位置，不因行数限制丢失。

**判断口诀**：**叙事类（摘要）靠压缩，字典类（设定表）靠分层。**

## 5.1c 规则库是第三个膨胀源，且**必须配触发词索引**

盘完所有文档会发现：摘要、设定表都已治理，**只剩规则库没有上限、只增不减**。它和设定表同类（字典 + 流程），所以同样**不能蒸馏、只能分层**：核心层 + 长尾层（按需 grep）。

⚠️ **只把「长尾内容」下沉还不够**：核心层里的「工作方式」节（拉表 / 校验清单 / 批注格式）其实是**做法**，每批只用一次，却常占核心层近三成——这类也要下沉。教训：**分层时要问「这条是规范还是用法」，而不是「这条长不长」**。

**但规则库多了一个设定表没有的陷阱——「不知道自己不知道」。**

设定表的条目是**事后查**的（写到某角色才查他），所以放哪层都行。规则不同：像「穿戴变化联动核数量及动作」「含性暴力意象的比喻要换喻体」这类规则，**你不记得它存在，就根本不会想到要查**——分层之后漏掉它们，改写质量会直接下降。

**解法：核心层带一张「触发词索引」表**，覆盖**全部**规则（含长尾），格式是 `触发词 / 场景 | 规则号 | 一句话要点`，约 20 字/条——100 条也才 2000 字。改文时按目标扫索引，再按实际问题进细则；命中词只帮助定位，无关键词的隐含或跨段问题仍须主动检查。索引、必要常驻判断和批末复核共同防止分层后漏执行。

**补充规则**：① 隐性错误类规则（grep 扫不出的）**要点必须常驻核心**，不能只留索引；② 新增长尾规则时**必须同步在索引加一行**，否则等于没写；③ 每批收尾的校验清单要覆盖长尾项。

**第四个膨胀源：项目记忆文件的「已定案决策」表**。它每轮注入却只增不减，早晚挤爆。**处置：移到决策记录文件（按需读），记忆文件只留极简索引 + 指针。**

**四条判断规则归总**：

| 内容性质 | 治理手段 | 例子 |
|---|---|---|
| 叙事（事件流水） | **压缩** | 滚动摘要 |
| 字典（可事后查） | **分层归档** | 设定表角色 |
| 流程（须主动想起） | **分层 + 触发词索引** | 规则库 |
| 决策定案 | **移出高频文件，只留索引** | 记忆文件决策表 |

> **实况修正**：记忆文件的决策表**往往并未真正移走**——实测项目里它至今仍保留「已定案决策」节，靠**人工下沉**压回线内。**它是唯一持续贴线的文件。** 原因也真实：**每轮必读的文件最难治理**——不能像设定表那样「移出不读」。所以这一行的正确读法是：**它是优先下沉对象，不是已解决的问题。**

## 5.1d SKILL.md 自身的常驻层准入（skill 文件也会膨胀，且比项目文件更贵）

SKILL.md 是**整份加载、全程占位**的容器——项目文件还能只 grep 局部，它一克都省不掉，所以比设定表更需要管。但**不设数字线**（硬上限逼出无意义的措辞挤压，见 5.0-3）：

> **与 rules.md 4.40 的关系**：机制同源，分工不同——**4.40 管项目侧常驻文件（规则库 / 设定表 / 项目记忆）的超限下沉，本条只管 SKILL.md 自身**。项目规则保存本书已采用的判断及设定指针，注明版本与来源；通用细则改版后须明确迁移，不能认为项目自动同步，也不把本书专有条件反推为通用规则。

- **准入判据**：常驻层只装「**不读会导致改错**」的判断（判据、红线、触发词、反向清单）；**开机类动作**（建项目、提问模板）与**论证 / 踩坑叙事**一律进 references。
- **按内容分工维护**：rules.md保存通用完整判据，SKILL.md保留执行要点及入口，checklist保存验收方法，项目文件保存本书已确认决定及采用版本。重复论证／全文改为指针，不能删掉入口必需的关键判断；硬护栏全文镜像是明确例外，由verify.py核对一致。历史案例须注明前提，不能覆盖现行规则。
- **分层写法与验收**：常驻条目保留「问题／触发词标题 + 关键判断 + `→ 规则号`」，完整细则放按需层，判据不得从整套规则中丢失。用真章节验收两件事：① 入口能识别问题、守住关键红线并触发正确查阅；② 沿指针能找到完整判据并完成场景判断。入口漏识别则补关键判断或索引，目标缺判据则修目标；不要求仅靠入口独立决定全部细节，也不因此搬回整条细则。
- **下沉前必须验证指针目标存在且含该判据**——空洞指针比没有指针更糟（5.3-5）。
- **禁止下沉的黑名单**：闸门类判据、红线、反向清单、触发词入口——这类「想不起来就漏执行」的内容（5.3-12）。

**软目标怎么定（借实测：一条线连调四次后立下的规矩）**：

- **软目标是「异常信号」，不是「常态边界」。** 把常态值定成上限，每次正常增长都触发，反而制造高频整理动作——**形同虚设的上限比没有上限更糟**。调整链必须有终点：立一条「这是最后一次调整」，之后只靠批尾体检盯数字。
- **连续两批超才下沉**，单次波动不触发——软目标是提醒线，不是硬顶。
- **维护失控按结果判断**：按rules 4.40核对反复挤字、整理无效、事实／判据丢失及指针损坏；不以工具调用次数判定，正常分文件处理不算失控。复核通过即收工。
- **容器反复超限，先收紧准入，别先调上限**——调线是治标，收准入是治本（实测准入收紧后一次收干）。

**容器准入闸门（新容器不是想建就建）**：

1. **第 0 步必建的**——照建，无判断；
2. **init.md 目录骨架列了触发条件的后期容器**——触发条件到了才建，没到就**不许在文件里当成既有结构引用**（本项目实例：规则库头部写了「下沉 `RULES-DETAIL.md`」，但该文件从未建——把「以后可能有」写成了「现在就有」，读者照空指针找细则）；
3. **两类之外的**——过三道：① 列出待存内容及现有位置的具体缺口（无法清楚归属、内容混放导致误读／重复冲突、或已满足既定下沉条件），先核在现有位置调整结构／索引能否解决；仅称“装不下”或“不方便”不够；② 归属判定：本书特有 → 项目侧，换书还要用 → skill 侧 references；③ 确需新建时**登记进 init.md 目录骨架**，建成后核入口与指针，未建前不当既有文件引用。

## 5.2 保存、归档与备份：先保内容，再选工具

- **通用要求**：明确权威正文来源，保存／整理前核修改位置、顺序、完整性及冲突，写后复核。既有项目沿用已定载体；Word、纯文本或其他文档使用各自适用方法，不为套脚本强转。默认Markdown流程直接写`text/vol-00N.md`、每100章一卷、不建单章；生成整合稿不是第二份可编辑正文。
- **位置指针**：保存章号和短引文，必要时加文档／卷标识；行号可辅助定位但会随编辑变化，不能只靠旧行号写回。
- **覆盖／清理来源前核可恢复性**：确认完整目标与独立可恢复备份；保留源文件的可逆整理与删除唯一副本分开处理。备份可以是已验证的本地独立副本或已授权远程副本，不把远程仓库作为所有项目的前提。
- **脚本二选一**：`--archive` 追加归档（按章号识别同章，写入前校验顺序与内容冲突，保留单章源文件）；无参数生成整合稿，**正文来源必须明确**，卷与单章混存时拒绝静默择一。卷内重号、乱序、缺章或同章内容冲突须先报告；源文件保留，输出按单文件原子替换，不承诺跨卷事务回滚。清理单章的顺序见 init.md。

## 5.3 硬约束与做法

1. **字数口径统一为「去空白字符数」，禁止裸 `wc -m`**——编辑工具会给 Markdown 补对齐空格，裸字符数虚高数倍（实测某文件 13,588 → 39,520，去空白后仍 13,254）。**误判的代价是真实的内容损失**：曾据此判定两个文件「双双超线」并已动手删冗余，按正确口径重算后发现**四个文件全在线内**。**判断膨胀前必须先确认口径。**
2. **批尾体检必须带「膨胀判断」，不能只记录数字**——实测各常驻文件去空白字符数，逐一对比项目预警线及上批状态，写明判断与处置。**连续两批超同一预警线才整条下沉**；单次超线只记录并跟踪，上批未测时不能推断为连续超线，不逐字挤压或反复抬线。
3. **跨文件重复审计值得每几批跑一次**——实测 26 个 md 去标点后比对（≥10 字）只出 7 条重复，**唯一真缺陷是「硬护栏在三个文件各抄一遍且已不同步」**（一处 4 条、一处只有 3 条）。**低成本、高命中，专门抓「抄列必然不同步」。**
4. **权威、入口与验收分别维护**——完整细则集中，入口保关键判断与指针，清单说明怎样检查。必要镜像明确列例外并同步核验；当前硬护栏由rules 4.10为权威、SKILL末尾保全文镜像，verify.py逐条核对，不能直接删镜像或削减护栏来去重。
5. **引用有效性快查**——批尾顺手核一遍常驻文件里引用的路径是否还存在。实测靠这条发现引用了一个已删除的文件。**空洞指针比没有指针更糟**（写了「论证见 DETAIL」但 DETAIL 里根本没有）。
6. **单一真相源**——新事实只进设定表，批注只记「改了什么」，不再两边写。实测某派生卡与设定表双写同一批角色，造成 **5 例不同步**。
7. **容器反复超限时，先问「准入是什么」，不是「上限提到哪」**——某快速查阅容器的字数线连调四次仍触顶；收紧准入（只放「性别 + 称呼」）后一次收干。**上调是治标，收准入是治本。**
8. **会变的数据一律不进常驻层**——等级、装备、技能、数值（血量 / 金价）、字数读数，写下即过时。**例外**：该物品 / 技能本身即剧情约束（不可摘的戒指、必须保密的变身术）。**静态世界观（如城市分区）要记。** 同理，**规则里不要写死会变的读数**（「现 2588，余量 400」改一次烂一次）——只留观察线 + 现测命令。
9. **长篇连载的数值矛盾不修**——前后矛盾是常态，改写者去管**收益接近零而风险不对称**：为修一个数值矛盾而改坏原著（改了装备件数）是赔本买卖。**只管两类**：性转引入的（按改后穿戴／机制核实实际件数）、明显写错会伤及情感线 / 人设的。
10. **机械约束用机械校验，语义判据用上下文证据**——章节完整性、ID 集合、结构、检索成本可用可数指标；人物、语气、审美与文学效果须说明判断依据，并以成对样例和完整语境复核。不能因无法精确计数而强用词频、维度占比或动作次数替代文学效果。格式检查先服从项目约定：换行符、全角缩进、尾空行可按约定机械检查，CRLF 不是所有项目的正文错误；工具通过只表示相应机械项通过。
11. **工具与授权分别判断**：本地提交按项目约定，远程推送、上传及发布分别依用户授权；保存／归档不自动授权外部操作。使用Git、云盘或文档平台只是实现选择，无远程项目也可在备份可恢复、内容可核验的前提下完成本地整理。已授权远程操作失败时据实际状态处理，不能引用历史重试次数自动扩展动作。
12. **「定了规则」≠「规则进链」——断链是比「规则不够」更隐蔽的失败**：一条规则若只写进**按需层**（沉淀文档 / DETAIL），而**没进每轮必读的核心层、也没在触发词索引里挂名**，那它**等于不存在**——每轮根本读不到，自然不执行。实测实例：补女性化描写规则拍板后只在沉淀文档落了板，核心层与索引都没有，于是**连续 30 章全部漏执行**（只去男码、漏补女码）；更糟的是**「规则库零新增」的读数把这失败藏住了**。**修法**：规则**同时**写进「每轮核心层（哪怕只留一行指针）＋ 触发词索引」，细则才放按需层。**完成标准**：一条规则「拍板后」的标志是**核心层可见**，不是「文档里写了」。

13. **区分 skill 版本与项目采用版本，并处理存量**——更新 skill 不会自动修改既有项目规则或正文。项目在决策记录写明采用版本 / 更新标识、日期与变更来源（用户明确要求 / 通用一致性约束 / 待验证建议）；待验证建议不自动成硬规则。语义规则或判据变化时，先评估已改章节的受影响范围，检索并复核，完成修订或显式记录待复核章节、原因与后续批次。范围大可分批，未完成不得声称旧稿全部符合新版。仅措辞、链接或索引整理，无语义变化时不强制全书重审。
