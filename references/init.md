# 基础文件：骨架、格式与创建时机

`SKILL.md` 第 0 步的执行细则。**改第 1 章前读一次**，之后按需回查。

## 创建顺序是单向依赖，不可跳步

```
feasibility.md（决策）→ GLOSSARY.md（设定表）→ RULES.md（规则库）
```

`CAST.md` / `MAINTENANCE.md` 等后期容器见下方「第二块」——触发条件与建法只写在那一片，此处不留第二份。

| 文件 | 何时创建 | 格式要点 |
|---|---|---|
| `feasibility.md` | **改第 1 章前**，用户逐项拍板后 | §0 决策总表：改造幅度 / 主角名 / 谁女性化 / 尺度 / 结局；**主要感情线方向、人物感情人设与进展方式**（见 rules.md 4.45）；**采用的 skill 版本或更新标识与日期**。只记定案，不记论证 |
| `GLOSSARY.md` | 同上，**与决策同步** | 角色处置表（原名 / 新名 / **性别** / 处置 / 性格 / **称呼映射**）＋ 人物进度（自知 / 知道对方 / 双方确认 / 旁人所知分别记）＋ 待核查。条目 ≈80 字/行 |
| `RULES.md` | 从设定表提炼，**遇到不可归约的新问题才补**，可长期零新增，不设每章产规则预期 | 编号规则表：`0.x` 硬护栏 / `1.x` 角色 / `2` 称呼替换 / `3` 描写 / `4.x` 隐性错误 ＋ **长尾索引**（触发词 → 规则号 → 一句话要点） |
| `CAST.md` | 每轮都要扫的**在场角色 >12 个**（后期容器，见下方第二块） | 准入＝「性别＋称呼」＋ ≤12 字身份；背景 / 进度 / 论证一律下沉 `GLOSSARY`。30 章未提及 → 退出本卡（设定表侧移入归档层，**不是删除**） |
| `MAINTENANCE.md` | 本书特有校验项多到 skill checklist **真装不下**时（后期容器，见下方第二块） | 放本书专属项及工具用法，通用模板引用checklist；已有项目可沿用本文件为维护入口 |
| `notes/batch-NN.md` | **每10章（批尾）** | 通用模板见[checklist.md](checklist.md)末尾；既有项目同步必填字段 |
| `text/vol-00N.md` | 每 100 章一卷 | 章标题 `## 第NN章《标题》`；改文**追加到文件末尾** |

## 目录骨架（三块：先建第一块，第二块触发后才建，第三块不建）

**第一块 · 基础文件（前三份第 0 步建；notes / vol 随流程建）：**

```
<项目根>/
  feasibility.md       ← 决策记录（改造方向与边界，只记定案）
  GLOSSARY.md          ← 设定表动态层（角色处置＋进度＋待核查）—— 不每轮读，按需 grep
  RULES.md             ← 规则库核心层（只放改文随手要用的规范）
  notes/batch-NN.md    ← 每 10 章一份批尾体检
  text/vol-00N.md      ← ★ 正文真相源（每 100 章一卷），可直接编辑
```

**第二块 · 触发后才建（⚠️ 未建前，任何文件不得把它当成既有结构引用——「下沉 RULES-DETAIL.md」这类话，容器没建就不许写）：**

| 容器 | 触发条件（可数） | 建时要点 |
|---|---|---|
| `RULES-DETAIL.md` | ① 核心层**细则行占比 >1/3**（细则行＝含踩坑 / 实例 / 成对反例写法的行）；或 ② 确认一条规则需 **≥2 次检索** | 整条下沉，核心层留索引；按需 grep |
| `CAST.md` | 每轮都要扫的**在场角色 >12 个** | 准入＝「性别＋称呼」＋ ≤12 字身份；30 章未提及 → 退出本卡（设定表侧移入归档层，**不是删除**；主角亲属 / 核心同伴 / 已拍定处置 / 长期对手不退出，见 structure.md 5.1b） |
| `MAINTENANCE.md` | 本书特有校验项多到 skill checklist **真装不下**时 | 放本书专属项及工具用法，通用模板引用checklist；已有项目沿用已定维护入口 |
| `GLOSSARY-STATIC.md` | 静态块字数 **> 动态层一半** | 作品事实 / 术语 / 主角基线 / 结局 / 校验口径 |

**第三块 · 不建**（实测价值被规则＋反例取代）：滚动摘要（直写卷后靠 grep 章标题定位）、前 3 章范本。

**容器准入**：不在一 / 二两块里的新容器，过闸门——① 现有容器真装不下（不是用起来不方便）；② 本书特有→项目侧，换书要用→skill 侧；③ **登记进本表第二块**（细则 → structure.md 5.1d）。

> **容器与机械操作的判据应可测**：「读着累 / 吃力 / 散架」这类主观词**不许当触发条件**——AI 没有「累」的体感，写上去等于没写（同 structure.md 5.3-10）。三个可数代理，按优先级：**动作计数**（凑齐一个动作需几次检索：1＝健康；2＝正常——按需进 structure 5.1d；≥3＝散架，该调入口 / 合并）＞**结构占比**（细则行 ÷ 总行数）＞**字数**（仅用于「连续两批超同一线」的提醒；线由项目自定并记录调整链终点——软目标是异常信号，不是常态边界）。**此处数字代理只衡量检索、结构和维护成本，不用于人物、语气或女性形象质量。语义判据须解释具体上下文并用成对样例复核，不能用词频替代文学效果。**

**注意目录树本身也会过期**——曾出现「目录树里列着一个早已删除的文件」。批尾顺手核一遍引用是否还存在。

## 采用版本与规则变更

新项目在 `feasibility.md` 记录采用版本；既有项目更新 skill 不会自动更新正文或项目规则。语义判据变更时记录是否采用、影响章节、已复核 / 已修订范围和待复核范围，按 structure.md 5.3-13 执行；单纯索引或措辞调整不自动触发全书重审。

## 项目记忆：只留一行指针

平台有项目级记忆机制时，**不要把设定搬进去**——它每轮注入、只增不减，早晚挤爆。

**平台无关的等价要求**：在项目记忆 / 常驻上下文中保留**一行指针**，指向设定表与规则库的路径。目的只有一个——**换会话时第一件事就能找到它们，而不是靠猜。**

## 批尾体检模板

通用模板与校验清单同在[`checklist.md`](checklist.md)末尾，此处不留第二份。已有项目可沿用MAINTENANCE等维护入口，同步checklist的必填记录项；本书专属填法留项目侧，不复制另一份通用模板。

## 脚本

`scripts/build-merged.py`（随 skill 附带，拷进项目根即可）：

- `python build-merged.py` —— 把 `text/` 下已明确的正文来源拼成**整合稿** `text/merged-*.md`（生成物，`.gitignore` 排除）；卷与单章混存时拒绝静默择一，先归档或核清来源。
- `python build-merged.py --archive` —— 把单章按卷追加进 `text/vol-00N.md`，**保留单章源文件**；按章号识别同章并检查顺序 / 冲突，同号内容不同须停止报告，不静默覆盖。

写入前先完成输入校验；写文件采用**单文件原子替换**，不承诺整个多卷操作可一起回滚。失败时检查哪些输出已更新，保留源文件后再处理，不能把单文件原子性解释为跨文件事务。

**安全顺序（写死在流程里，不要跳步）**：commit → push → 确认远程同步 → 才跑 `--archive` → 核对卷文件章节、顺序与内容完整 → 如需清理再手动删已归档单章 → 再提交。脚本不删除单章；清理前须有完整卷及远程备份，**未推送的历史只在本机，丢了就没了**。
