# 基础文件：骨架、格式与创建时机

`SKILL.md`第0步的执行细则。开始本书改写前读一次，之后按需回查；从中途章节开始也须核已定方向与规则，已有项目沿用有效文件，不为满足“第1章”或目录示例重建。

## 创建顺序是单向依赖，不可跳步

```
feasibility.md（决策）→ GLOSSARY.md（设定表）→ RULES.md（规则库）
```

`CAST.md` / `MAINTENANCE.md` 等后期容器见下方「第二块」——触发条件与建法只写在那一片，此处不留第二份。

| 文件 | 何时创建 | 格式要点 |
|---|---|---|
| `feasibility.md` | **开工前**，核现有决定或经用户确认后 | §0 决策总表：改造幅度 / 主角名 / 谁女性化 / 尺度 / 结局；**主要感情线方向、人物感情人设与进展方式**（见 rules.md 4.45）；**采用的 skill 版本或更新标识与日期**。只记定案，不记论证 |
| `GLOSSARY.md` | 同上，**与决策同步** | 角色处置、称呼、已定形象及后续相关身份／关系约束，认知进度分别记；字段随本书题材和实际需要确定，不按行字数截断事实。未定项记待核 |
| `RULES.md` | 从设定表提炼，**遇到不可归约的新问题才补**，可长期零新增，不设每章产规则预期 | 编号规则表：`0.x` 硬护栏 / `1.x` 角色 / `2` 称呼替换 / `3` 描写 / `4.x` 隐性错误 ＋ **长尾索引**（触发词 → 规则号 → 一句话要点） |
| `CAST.md` | 每轮都要扫的**在场角色 >12 个**（后期容器，见下方第二块） | 准入＝「性别＋称呼」＋ ≤12 字身份；背景 / 进度 / 论证一律下沉 `GLOSSARY`。退出按本书已定归档条件复查；设定整条保留，卡的精简不删权威事实 |
| `MAINTENANCE.md` | 确需本书专属维护入口时；按下方第二块核具体缺口 | 放本书专属项及工具用法，通用模板引用checklist；已有项目可沿用本文件为维护入口 |
| `notes/batch-NN.md` | **每10章（批尾）** | 通用模板见[checklist.md](checklist.md)末尾；既有项目同步必填字段 |
| `text/vol-00N.md` | 默认Markdown载体，每100章一卷 | 章标题`## 第NN章《标题》`；新章按序追加，重改则定位原章精修；既有项目沿用其已定载体 |

## 目录骨架（三块：先建第一块，第二块触发后才建，第三块不自动建）

**第一块 · 基础文件（前三份第 0 步建；notes / vol 随流程建）：**

```
<项目根>/
  feasibility.md       ← 决策记录（改造方向与边界，只记定案）
  GLOSSARY.md          ← 设定表动态层（角色处置＋进度＋待核查）—— 不每轮读，按需 grep
  RULES.md             ← 规则库核心层（只放改文随手要用的规范）
  notes/batch-NN.md    ← 每 10 章一份批尾体检
  text/vol-00N.md      ← ★ 正文真相源（每 100 章一卷），可直接编辑
```

**第二块 · 触发后才建（⚠️ 未建前，任何文件不得把它当成既有结构引用——「下沉 RULES-DETAIL.md」这类话，容器没建就不许写）：**

| 容器 | 触发条件（可核对） | 建时要点 |
|---|---|---|
| `RULES-DETAIL.md` | ① 核心层**细则行占比 >1/3**（细则行＝含踩坑 / 实例 / 成对反例写法的行）；或 ② 因索引缺口／内容分散，确认一条规则需 **≥2 次重复搜索**，且调整现有入口仍不能解决 | 整条下沉，核心层留关键判断与有效索引；沿有效指针读取完整细则不算重复搜索 |
| `CAST.md` | 每轮都要扫的**在场角色 >12 个** | 准入＝「性别＋称呼」＋ ≤12 字身份；退出按本书已定条件复查重要性及后续约束；权威设定完整保留，核心人物／未收伏笔保留入口（见structure.md 5.1b） |
| `MAINTENANCE.md` | 有本书专属校验／工具说明，核现有规则、设定及批注后仍无法清楚归属，或分散存放已导致漏查／重复冲突；须说明待存项、现有位置及调整结构／索引仍不能解决的具体缺口 | 放本书专属项及工具用法，通用模板引用checklist；已有项目沿用已定维护入口 |
| `GLOSSARY-STATIC.md` | 静态块字数 **> 动态层一半** | 作品事实 / 术语 / 主角基线 / 结局 / 校验口径 |

**第三块 · 不自动建**：重复的滚动摘要、前3章固定范本等。先用现有设定、批注及正文位置接续；确有缺口时按structure 5.1及容器准入判断，不以单章／卷等载体或固定章数决定必要性。

**容器准入**：不在一 / 二两块里的新容器，先列待存项、现有位置和具体归属／检索缺口，核调整结构或索引能否解决，再按structure.md 5.1d判断是否需独立容器；不能只用“装不下／不方便”作依据。本书特有→项目侧，换书要用→skill侧；确需新建时**登记进本表第二块**并核有效入口。

> **容器与机械操作的判据应可复核**：说明待存项、检索路径及具体缺口，不以“读着累／吃力／散架”等主观词作依据（同structure.md 5.3-10）。可记录同一问题的重复搜索、细则行占比和去空白字符数，定位维护成本；沿有效指针按需查阅或正常分次读取不算无效检索，不因总次数多就判结构失效、强制合并或新建。字数仅按项目已定线跟踪，连续两批超同一线再下沉。**这些指标不用于人物、语气或女性形象质量；语义判据仍用上下文证据和成对样例复核，不能用词频替代文学效果。**

**注意目录树本身也会过期**——曾出现「目录树里列着一个早已删除的文件」。批尾顺手核一遍引用是否还存在。

## 采用版本与规则变更

新项目在 `feasibility.md` 记录采用版本；既有项目更新 skill 不会自动更新正文或项目规则。语义判据变更时记录是否采用、影响章节、已复核 / 已修订范围和待复核范围，按 structure.md 5.3-13 执行；单纯索引或措辞调整不自动触发全书重审。

## 项目记忆：只留一行指针

平台有项目级记忆机制时，**不要把设定搬进去**——它每轮注入、只增不减，早晚挤爆。

**平台无关的等价要求**：在项目记忆 / 常驻上下文中保留**一行指针**，指向设定表与规则库的路径。目的只有一个——**换会话时第一件事就能找到它们，而不是靠猜。**

## 批尾体检模板

通用模板与校验清单同在[`checklist.md`](checklist.md)末尾，此处不留第二份。已有项目可沿用MAINTENANCE等维护入口，同步checklist的必填记录项；本书专属填法留项目侧，不复制另一份通用模板。

## 保存与脚本

通用要求见structure.md 5.2：先核正文权威来源、修改位置、顺序、完整性及可恢复性，再选择适合载体的工具。以下脚本仅处理规定格式的Markdown，Word等载体不为套脚本自动转换。

`scripts/build-merged.py`（随 skill 附带，拷进项目根即可）：

- `python build-merged.py` —— 把 `text/` 下已明确的正文来源拼成**整合稿** `text/merged-*.md`（生成物，`.gitignore` 排除）；卷与单章混存时拒绝静默择一，先归档或核清来源。
- `python build-merged.py --archive` —— 把单章按卷追加进 `text/vol-00N.md`，**保留单章源文件**；按章号识别同章并检查顺序 / 冲突，同号内容不同须停止报告，不静默覆盖。

写入前先完成输入校验；写文件采用**单文件原子替换**，不承诺整个多卷操作可一起回滚。失败时检查哪些输出已更新，保留源文件后再处理，不能把单文件原子性解释为跨文件事务。

**本脚本的归档顺序**：核来源／格式／章序／冲突及可恢复性 → 保留单章源文件执行`--archive` → 核目标卷章节及内容完整 → 如需清理来源，先确认完整目标与独立可恢复备份再操作。本地提交按项目约定；push、上传及发布分别依用户授权，无Git远程不阻止安全的本地归档。脚本不会删除单章，归档成功也不等于获得清理或外部操作授权。
